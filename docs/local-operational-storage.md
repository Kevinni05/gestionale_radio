# Operational data on Android

Queue snapshots, persistent idempotency keys and report drafts now use native SQLite transactions. Each value is encrypted independently with AES-256-GCM, a fresh random nonce and the logical record key as authenticated additional data. SQLite stores a SHA-256 identifier instead of the user/tenant/task storage key. The encryption key stays in Android Keystore; hardware backing depends on the device. This protects payloads at rest; it does not replace account authorization or protect a compromised running device.

Both queue recovery slots commit in one transaction. Existing actorUid/tenantId executor checks and panel isolation remain in place. Legacy preferences are migrated on access, copied to native storage, read back and compared before the plaintext copy is removed. If verification or the native layer fails, the caller receives an error and the original legacy data is retained. A stale legacy copy never replaces an existing native record. Authentication failure during decryption does not reset the database.

The platform channel runs disk and cryptographic operations on one worker thread. Android backup remains disabled. Do not uninstall, clear application data, rotate/delete the Keystore key or restore the database onto another installation while offline work is pending. App upgrades must preserve the application ID, signing identity, database and Keystore alias. A downgrade to a build that only reads SharedPreferences cannot recover migrated work: sync/export pending work before such a rollback.

Tests cover native AES-GCM tampering/key binding, random nonces, actual SQLite transaction rollback and reopening, plus Dart migration failure/verification/order and existing queue/draft regressions. Test keys in Robolectric are generated software keys; actual Android Keystore and forced process termination/upgrade still require two real-device acceptance runs. This storage implementation targets Android; unsupported platform channels fail closed instead of storing operational data in plaintext. Media files referenced by drafts have a separate lifecycle and are not encrypted by this record store.

Limits: at most 256 records per native transaction, 2,048 characters per logical key and 8 MB per UTF-8 value. The existing queue limit remains 200 actions. Device lock is the local access boundary; server authentication and revocation are still required before queued operations execute.

A dedicated authenticated key proof is checked whenever the database opens. A replacement or lost key blocks writes even to new records; an unreadable existing record cannot be overwritten by a normal save. Native tests include reopening with the wrong key and verifying that the original database remains usable with its original key. The offline panel surfaces native access errors with a retry action and instructions to preserve the installation.
